Where do the ONNX models come from, and how does this actually work?

PANOSTITCH runs fabio-sim/LightGlue-ONNX's RaCo-ALIKED-LightGlue+ pipeline models (v3.0 release) — a single fused ONNX graph that does feature extraction and matching for an image pair in one call. These are the exact same weights used by that project's own official browser (WebGPU/ONNX Runtime Web) demo, so the graph is already proven to run outside Python. Photo Suite's models\panoramamaker folder (filled by panostitch_setup_models.py) holds all seven keypoint variants; pick a different folder with the button above, or let the page download a variant straight from the GitHub release (cached after the first time). Bigger K = more keypoints = better matches on wide-baseline or low-texture scenes, at the cost of speed.

Unordered stitching: every photo is matched against every other photo, at a fixed 1280px matching resolution, so the drop order never matters. (An earlier version pre-screened pairs at a lower resolution first, but LightGlue's attention cost is dominated by the model's fixed keypoint budget rather than image size, so that screening pass cost almost as much as the real match — it was removed as pure overhead.) Matches become edges in a graph; PANOSTITCH keeps the highest-confidence spanning tree per connected group of photos and reports photos that didn't overlap with anything as unmatched, rather than guessing. Matching always happens at that fixed size regardless of the RES setting — ALIKED's backbone runs at full image resolution (not an 8x-downsampled grid like classic SuperPoint), so matching at your output resolution directly would need far more memory than finding the alignment needs; RES only controls how big the final composited panorama is, the same way desktop stitchers find control points on a small preview and render from the full-size originals.

Camera model: each accepted pairwise match gives a homography. From the whole graph, PANOSTITCH estimates one shared focal length and a 3D rotation per photo (the same simplifying assumption AutoStitch/Hugin use for a single lens), then renders onto your chosen projection — rectilinear for a flat, narrow-angle result; cylindrical for a classic wide horizontal panorama; equirectangular for full spherical/360° coverage. "Auto" picks cylindrical or equirectangular from how wide the estimated rotations spread. Seams are blended by distance-weighted feathering; an optional per-photo exposure-gain correction (off by default — enable it with the checkbox) can be solved across the match graph if your source photos have visibly inconsistent exposure, though it's estimated from just a handful of sample points per pair and can misfire on scenes with strong local lighting differences. This is pairwise-homography initialization only — there's no global bundle-adjustment refinement pass (yet), so very large or very wide-baseline sets will drift a bit more than a dedicated desktop tool like Hugin.
